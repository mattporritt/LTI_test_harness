# MDL-89973: provisional grades, completion and update ordering

Source: [MDL-89973](https://moodle.atlassian.net/browse/MDL-89973), read with all four
current comments on 28 October 2026. Jira type: **Improvement**, waiting for peer
review. This repository adds test-tool coverage; it does not implement the Moodle
fix or modify the issue. The latest comment distinguishes two tool policies:
ignore provisional values without clearing grades, or accept them through normal
grading. Both must support deliberate clearing and reject stale updates after a
clear. No stable Moodle branch or issue metadata is changed here.

## Why the previous harness missed it

The score action always sent `activityProgress:Completed` and
`gradingProgress:FullyGraded`, generated a fresh timestamp, and required a numeric
score. It could not reproduce the issue. The API and manual form now expose:

- All standard activity and grading progress values.
- A configurable positive `scoreMaximum` and non-negative `scoreGiven`, including
  decimals and extra credit above the maximum.
- An explicit null score or omitted score field for clearing tests.
- Caller-supplied timestamps, preserved verbatim, to test ordering and replay.
- An explicit line-item URL override so a previously created standalone item cannot
  silently become the target of an activity-completion test.

Default numeric requests remain Completed/FullyGraded with maximum 100. Missing a
score accidentally is rejected; deliberate omission requires `scoreMode:omit`.
The tool retains the exact outgoing JSON and LMS response. Standards reference:
[AGS 2.0 sections 3.4.4–3.4.9 and 4.7](https://www.imsglobal.org/spec/lti-ags/v2p0).

## Manual reproduction

1. Use a synthetic learner enrolled in a test course. Enable AGS grades and column
   management on the tool. Set activity maximum 100, grade to pass 50, and automatic
   completion requiring a passing grade. Enable the activity placement.
2. Launch as that learner. In the inspector choose the activity's advertised line
   item as **Line item URL**. The API equivalents can use `lineitemUrl` explicitly.
3. Clear the grade using score mode `omit`, activity `Initialized`, grading `NotReady`.
4. Send value 60/100, activity `InProgress`, grading `Pending`. Inspect the gradebook
   and completion, not just the HTTP response. With partial acceptance enabled in
   Moodle the grade should be 60 and completion passing; with it disabled no grade
   should be created. On the unpatched test branch the response was 200, grade null,
   completion incomplete.
5. Send 80 FullyGraded, then 90 Pending. With partial acceptance off, 80 must remain;
   with it on, 90 should be recorded. Existing passing completion must not disappear.
6. Send an older FullyGraded timestamp: it must not replace the newer state.
7. Clear explicitly with null, then send an older score; repeat using omitted score.
   Both stale updates must leave the grade cleared.
8. Finish with a fresh final grade. The automated runner restores 83 by default.

An AGS platform may choose not to record provisional scores; the test does not
classify that optional policy alone as a conformance violation. It asserts the
chosen policy and separately checks unintended grade erasure and stale updates.

## API examples

```json
{"action":"score","scoreGiven":60,"scoreMaximum":100,"activityProgress":"InProgress","gradingProgress":"Pending"}
```

```json
{"action":"score","scoreGiven":null,"activityProgress":"Initialized","gradingProgress":"NotReady"}
```

```json
{"action":"score","scoreMode":"omit","activityProgress":"Initialized","gradingProgress":"NotReady","timestamp":"2026-10-28T00:00:00.000Z"}
```

## Automated real-Moodle regression

`_smoke_test/ags-partial-scores.js` uses the selected learner launch's advertised
activity line item, posts each update through the harness, and reads actual grades
and completion using `_smoke_test/moodle-completion.php` in the selected Moodle
container. The observer is read-only unless explicitly passed `--configure`.
Configuration mode is restricted to `LTI-HARNESS-` courses and `harness_` users.
It enables course completion, sets automatic passing-grade completion, and sets
maximum 100 / grade to pass 50 on the dedicated activity. It does not enable site
completion globally; that must already be enabled. It works with mod_lti tables
on stock Moodle and core_ltix's activity placement alike.

For the retained local fixture:

```sh
# Copy the observer to a temporary container path, not into Moodle source.
docker cp _smoke_test/moodle-completion.php moodlemaster-webserver-1:/tmp/lti-harness-completion.php
docker exec moodlemaster-webserver-1 php /tmp/lti-harness-completion.php /var/www/html/config.php 12 5 --configure

# Export HARNESS_TOKEN and the public CA path locally; do not commit credentials.
HARNESS_URL=https://lti-harness.127.0.0.1.nip.io:8444 \
LAUNCH_ID=4892e570-271f-4790-a38c-b1d0a9472d07 \
MOODLE_CONTAINER=moodlemaster-webserver-1 MOODLE_CMID=12 MOODLE_USERID=5 \
node _smoke_test/ags-partial-scores.js > _smoke_test/artifacts/moodle/MDL-89973.json
```

Set `NODE_EXTRA_CA_CERTS` for the host Node process when using the local CA. Change
all IDs/container/config path for another instance. With a separately initialized
PHPUnit/Behat site, select that site's own config/database and corresponding launch;
never observe the development database while sending scores to an acceptance site.

`ACCEPT_PARTIAL_SCORES=false` (default) asserts ignore-with-preservation policy.
`true` asserts acceptance of provisional grades and completion. This variable does
**not** configure a Moodle setting. Use it to match the behavior/setting under test.
The old branch is expected to fail. The runner exits **1** if any expected grade or
completion state is wrong, even when all HTTP requests succeeded. Both corrected
policies and the buggy behavior are covered by independent scenario tests.
It spaces fresh events across Moodle's second-resolution timestamp boundary, keeps
stale timestamps deliberately older, and restores a fresh final test grade
in cleanup, removes its temporary observer copy, and leaves the fixture available.

## Observed real results

Moodle `6.0dev (Build: 20261021)`, `lti-analysis/baseline-core`, commit
`ddca0b0fb1e5c7c10575ccd9469d23594988f77c`, `https://webserver`.
All score requests returned HTTP **200**. Policy asserted: ignore provisional scores.

| Step | Grade observed | Completion observed | Outcome |
| --- | --- | --- | --- |
| Clear | null | incomplete (0) | Expected |
| Pending 60 | null | incomplete (0) | Existing policy; demonstrates the original use case |
| FullyGraded 80 | 80 | passing (2) | Expected |
| Pending 90 after final | **null** | **incomplete (0)** | **Exposes grade/completion erasure** |
| Older final 10 | **10** | failing (3) | **Stale update wrongly accepted** |
| Explicit null clear | null | incomplete (0) | Expected |
| Older final 30 after clear | **30** | failing (3) | **Stale update wrongly accepted** |
| Fresh final 70 | 70 | passing (2) | Expected |
| Omitted-score clear | null | incomplete (0) | Expected |
| Older final 40 after clear | **40** | failing (3) | **Stale update wrongly accepted** |
| Cleanup restoration | 83 | passing (2) | Fixture restored |

When erased, `grade_grades.timemodified` was also null. This confirms the ticket's
previously code-read grade-erasure concern on this real test branch, not merely a
synthetic simulation. The report is local under the ignored smoke artifacts;
no raw access tokens are included. A failing regression run here is evidence that
the harness exposes the issue, not a failed harness unit suite or a Moodle fix.
